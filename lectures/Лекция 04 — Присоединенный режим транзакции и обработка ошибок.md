# Лекция 4 Присоединенный режим транзакции и обработка ошибок

**Дисциплина:** ADO.NET  
**Продолжительность:** 2 академических часа — 90 минут  
**Предварительные знания:** лекции 1–3; параметры, `ExecuteNonQuery`, `SqlException`, `using`, первичные и внешние ключи.  
**Среда:** Windows, консольный проект C# с `Microsoft.Data.SqlClient`, база `CollegeAdo` из лекции 2.

При переводе студента в другую группу нужно изменить его карточку и добавить запись в историю переводов. Если первая команда выполнится, а вторая завершится ошибкой, журнал окажется в несогласованном состоянии. Объединим обе команды в транзакцию, чтобы сохранять их изменения вместе.

После занятия вы сможете создать `SqlTransaction`, связать с ней команды, подтвердить изменения через `Commit`, выполнить `Rollback` при ошибке и проверить, что изменена именно ожидаемая запись. Лекция продолжает присоединённый режим: работа выполняется через открытое подключение, без `DataSet` и `DataAdapter`.

## Почему двух команд недостаточно

В лекции 3 каждый метод самостоятельно открывал подключение и выполнял одну операцию. Для независимых действий этого достаточно. Теперь у нас одно прикладное действие из двух шагов:

1. Изменить `Students.GroupName` у выбранного студента.
2. Добавить строку в `StudentTransfers` с прежней и новой группами.

Представим, что между шагами возникла ошибка. Пользователь увидит новую группу, но не найдёт записи о переводе. Если поменять порядок команд, проблема сохранится: может появиться история перевода без изменения карточки.

**Транзакция** объединяет несколько операций с базой в одно целое. Успешное выполнение подтверждают, а при отказе отменяют неподтверждённые изменения этой транзакции. Для локальной транзакции ADO.NET используется одно подключение. [Локальные транзакции ADO.NET](https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/local-transactions).

Транзакция не исправляет неверную логику автоматически. Если программа изменяет не того студента, обе команды могут успешно зафиксировать неправильное действие. Поэтому условия `WHERE`, параметры и проверки количества строк остаются обязательными частями решения.

## BeginTransaction Commit и Rollback

| Действие | Вызов | Смысл |
| --- | --- | --- |
| Начать | `connection.BeginTransaction()` | Получить объект локальной транзакции |
| Включить команду | `command.Transaction = transaction` | Связать команду с этой транзакцией |
| Подтвердить | `transaction.Commit()` | Зафиксировать выполненные изменения |
| Отменить | `transaction.Rollback()` | Откатить неподтверждённые изменения |

Сначала открывают подключение, затем начинают транзакцию. Все участвующие команды используют это же подключение и объект транзакции. Удобно передать их конструктору `new SqlCommand(sql, connection, transaction)`.

```text
Open
  ↓
BeginTransaction
  ↓
UPDATE Students
  ↓
INSERT StudentTransfers
  ↓
Commit

Ошибка до успешного завершения → попытка Rollback → сообщение об ошибке
```

Успешный `ExecuteNonQuery` первой команды ещё не завершает прикладную операцию: впереди вторая команда и подтверждение. Сообщение «Перевод сохранён» выводим только после успешного `Commit`.

## Таблица истории переводов

Один раз выполните скрипт в SSMS, подключившись к той же локальной базе, что и в лекции 2. Таблица `Students` уже должна существовать.

```sql
USE CollegeAdo;
GO

CREATE TABLE dbo.StudentTransfers
(
    TransferId int IDENTITY(1, 1) NOT NULL
        CONSTRAINT PK_StudentTransfers PRIMARY KEY,
    StudentId int NOT NULL,
    FromGroup nvarchar(20) NOT NULL,
    ToGroup nvarchar(20) NOT NULL,
    ChangedAt datetime2 NOT NULL
        CONSTRAINT DF_StudentTransfers_ChangedAt DEFAULT SYSUTCDATETIME(),
    CONSTRAINT FK_StudentTransfers_Students
        FOREIGN KEY (StudentId) REFERENCES dbo.Students(StudentId),
    CONSTRAINT CK_StudentTransfers_DifferentGroups
        CHECK (FromGroup <> ToGroup)
);
GO
```

Первичный ключ отличает записи истории. Внешний ключ связывает перевод с существующим студентом, а ограничение `CHECK` запрещает запись перевода в ту же группу. Время записывает сервер в UTC.

Внешний ключ также не позволяет просто удалить студента, на которого ссылается история. В реальной системе нужно отдельно определить правила хранения таких записей. Для этой работы сохраняем историю и не включаем каскадное удаление.

## Проверка ожидаемой группы

Два сотрудника могут открыть одну карточку и увидеть группу ИСП-21. Первый переведёт студента в ИСП-22. Второй не должен незаметно записать перевод «из ИСП-21», опираясь на уже устаревшие сведения.

Включим ожидаемую исходную группу в условие обновления:

```sql
UPDATE dbo.Students
SET GroupName = @toGroup
WHERE StudentId = @id AND GroupName = @fromGroup;
```

Если изменилась группа или студент удалён, команда затронет ноль строк. Приложение остановит перевод и предложит перечитать данные. Это пример проверки исходного значения при обновлении. [Оптимистическая конкуренция](https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/optimistic-concurrency).

Проверка относится только к группе. Изменение почты она не обнаруживает, а изменение группы с последующим возвратом к прежнему значению тоже может остаться незаметным. Если требуется обнаруживать любое изменение строки, нужен более полный механизм контроля версии, например отдельный столбец `rowversion`.

Проверка и обновление выполняются одной SQL-командой. Отдельное предварительное чтение группы без такого условия оставило бы промежуток, в котором другой пользователь мог изменить данные.

## Полная программа перевода студента

Создайте консольный проект `AdoNetLesson04`, установите пакет `Microsoft.Data.SqlClient` и поместите следующий код в `Program.cs`. На исходных данных студент с ID `1` — Анна Иванова из ИСП-21.

Вначале `simulateFailure` равно `true`: программа специально вызывает исключение после изменения карточки, чтобы продемонстрировать откат. Для успешного перевода переключите флаг в `false` после проверки первого сценария.

```csharp
using System;
using System.Data;
using Microsoft.Data.SqlClient;

string connectionString =
    @"Server=(localdb)\MSSQLLocalDB;Database=CollegeAdo;Integrated Security=True;Encrypt=False;";

bool simulateFailure = true;

try
{
    TransferStudent(
        connectionString,
        studentId: 1,
        fromGroup: "ИСП-21",
        toGroup: "ИСП-22",
        simulateFailure: simulateFailure);

    Console.WriteLine("Перевод сохранён вместе с записью в истории.");
}
catch (SqlException ex)
{
    Console.Error.WriteLine($"Ошибка SQL Server {ex.Number}: {ex.Message}");
    Environment.ExitCode = 1;
}
catch (InvalidOperationException ex)
{
    Console.Error.WriteLine($"Операция не подтверждена: {ex.Message}");
    Environment.ExitCode = 1;
}
catch (ArgumentException ex)
{
    Console.Error.WriteLine($"Ошибка входных данных: {ex.Message}");
    Environment.ExitCode = 1;
}

static void TransferStudent(
    string connectionString,
    int studentId,
    string fromGroup,
    string toGroup,
    bool simulateFailure)
{
    if (studentId <= 0)
    {
        throw new ArgumentException("ID должен быть положительным.");
    }

    if (string.IsNullOrWhiteSpace(fromGroup) ||
        string.IsNullOrWhiteSpace(toGroup) ||
        fromGroup.Length > 20 || toGroup.Length > 20 ||
        fromGroup == toGroup)
    {
        throw new ArgumentException(
            "Укажите разные непустые группы длиной до 20 символов.");
    }

    using var connection = new SqlConnection(connectionString);
    connection.Open();
    using var transaction = connection.BeginTransaction();

    try
    {
        using var update = new SqlCommand(
            "UPDATE dbo.Students SET GroupName = @toGroup " +
            "WHERE StudentId = @id AND GroupName = @fromGroup;",
            connection,
            transaction);
        update.CommandTimeout = 30;
        update.Parameters.Add("@id", SqlDbType.Int).Value = studentId;
        update.Parameters.Add("@fromGroup", SqlDbType.NVarChar, 20).Value = fromGroup;
        update.Parameters.Add("@toGroup", SqlDbType.NVarChar, 20).Value = toGroup;

        int updated = update.ExecuteNonQuery();

        if (updated != 1)
        {
            throw new InvalidOperationException(
                "Студент не найден или исходная группа уже изменилась.");
        }

        if (simulateFailure)
        {
            throw new InvalidOperationException(
                "Учебная ошибка после UPDATE и до записи истории.");
        }

        using var insert = new SqlCommand(
            "INSERT INTO dbo.StudentTransfers (StudentId, FromGroup, ToGroup) " +
            "VALUES (@id, @fromGroup, @toGroup);",
            connection,
            transaction);
        insert.CommandTimeout = 30;
        insert.Parameters.Add("@id", SqlDbType.Int).Value = studentId;
        insert.Parameters.Add("@fromGroup", SqlDbType.NVarChar, 20).Value = fromGroup;
        insert.Parameters.Add("@toGroup", SqlDbType.NVarChar, 20).Value = toGroup;

        if (insert.ExecuteNonQuery() != 1)
        {
            throw new InvalidOperationException("Не записана история перевода.");
        }

        transaction.Commit();
    }
    catch
    {
        try
        {
            transaction.Rollback();
            Console.Error.WriteLine("Выполнен Rollback.");
        }
        catch (Exception rollbackError)
        {
            Console.Error.WriteLine(
                $"Не удалось подтвердить откат: {rollbackError.Message}");
        }

        throw;
    }
}
```

Обе команды передают значения параметрами и участвуют в одной транзакции. В примере используются таблицы без триггеров и обычные настройки подсчёта затронутых строк, как в лекции 3.

## Разбор обработки ошибок

Внутренний `catch` перехватывает ошибку всей последовательности, пытается выполнить откат и затем повторно выбрасывает исходное исключение через `throw;`. Так вызывающий код узнаёт, почему операция не завершилась.

Откат сам может завершиться ошибкой, например если подключение разорвано или транзакция уже завершена сервером. Поэтому попытка `Rollback` имеет собственный `try/catch`; сообщение о её проблеме не подменяет исходную причину. Такой порядок используется и в примере Microsoft по локальным транзакциям. [Обработка ошибок транзакции](https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/local-transactions).

Ошибка связи во время `Commit` требует особого внимания: приложение может не получить подтверждение уже выполненной фиксации. Перед повтором действия нужно проверить фактическое состояние базы. В этой учебной задаче проверяем карточку и историю запросами ниже; в системах с автоматическими повторами отдельно проектируют защиту от повторного выполнения.

`using` освобождает ресурсы и при исключении, но не заменяет осмысленное решение о фиксации. Успешный путь явно вызывает `Commit`, отказ — пытается выполнить `Rollback`.

## Проверка трёх сценариев

Перед первым запуском проверьте, что у студента `1` группа ИСП-21, а его история ещё пуста. Запросы выполняются после завершения программы:

```sql
SELECT StudentId, FullName, GroupName
FROM dbo.Students
WHERE StudentId = 1;

SELECT TransferId, StudentId, FromGroup, ToGroup, ChangedAt
FROM dbo.StudentTransfers
WHERE StudentId = 1
ORDER BY TransferId;
```

| Сценарий | Действие | Ожидаемый результат |
| --- | --- | --- |
| Ошибка между командами | Первый запуск с `simulateFailure = true` | Группа остаётся ИСП-21, новой истории нет, выводится сообщение об откате |
| Успешный перевод | Следующий запуск с `simulateFailure = false` | Группа становится ИСП-22, появляется одна запись ИСП-21 → ИСП-22 |
| Устаревшая исходная группа | Повторить успешный запуск с прежним `fromGroup` | `UPDATE` затрагивает 0 строк, новая история не появляется |

После успешного перевода исходная база уже изменена. Для обратного перевода поменяйте `fromGroup` на ИСП-22 и `toGroup` на ИСП-21. Это создаст отдельную запись истории; не удаляйте историю только ради совпадения с первым запуском.

Если вы ранее меняли учебные данные, используйте фактический ID и текущую группу. Ожидаемые результаты таблицы относятся к исходным данным и указанному порядку запусков.

## Короткие транзакции и тайм-ауты

Откройте форму, соберите ввод и получите подтверждение пользователя **до** начала транзакции. Затем выполните только необходимые команды и быстро завершите транзакцию. Открытая транзакция может удерживать блокировки, из-за чего другим операциям придётся ждать.

Есть два разных ограничения ожидания:

| Настройка | Где задаётся | Что ограничивает |
| --- | --- | --- |
| `Connect Timeout` | В строке подключения | Ожидание открытия подключения |
| `CommandTimeout` | У объекта команды | Ожидание выполнения и сетевого чтения результата команды |

`CommandTimeout = 30` задаёт 30 секунд для команды; это не общий лимит времени всей транзакции и не время, предоставленное пользователю на ввод. Значение `0` отключает ограничение ожидания команды. [CommandTimeout](https://learn.microsoft.com/en-us/dotnet/api/microsoft.data.sqlclient.sqlcommand.commandtimeout), [ConnectionTimeout](https://learn.microsoft.com/en-us/dotnet/api/microsoft.data.sqlclient.sqlconnection.connectiontimeout).

## Частые ошибки

| Ошибка | Последствие | Исправление |
| --- | --- | --- |
| Команды открывают разные подключения | Не получается одна локальная транзакция | Передать им общее подключение и транзакцию |
| Не назначено `Command.Transaction` | Команда не связана с активной транзакцией | Передать транзакцию в конструктор или свойство |
| `Commit` вызван после первой команды | Второй шаг уже не защищён той же границей | Подтвердить после всех шагов и проверок |
| Исключение перехвачено без отката и сообщения | Вызывающий код не понимает исход операции | Выполнить попытку отката и сохранить причину |
| В транзакции ожидают ввода | Продлевается удержание ресурсов | Собрать ввод заранее |
| Любую ошибку автоматически повторяют | Возможен повтор уже выполненного действия | Проверить результат и условия повторного выполнения |

## Контрольные вопросы

1. Почему два успешных SQL-запроса по отдельности не гарантируют целостность всей операции?
2. Какие объекты должны быть общими у команд локальной транзакции?
3. Чем `Commit` отличается от `Dispose`?
4. Зачем проверять, что `UPDATE` изменил ровно одну строку?
5. Почему откат помещён во вложенный `try/catch`?
6. Зачем после попытки отката используется `throw;`?
7. Почему при ошибке связи во время фиксации нельзя без проверки обещать, что изменений нет?

**Краткие ответы:** между отдельными командами возможен отказ; общими должны быть подключение и транзакция; `Commit` подтверждает изменения, `Dispose` освобождает ресурс; ноль строк означает отсутствие ожидаемой записи или группы; откат тоже может завершиться ошибкой; `throw;` сохраняет исходную ошибку для вызывающего кода; сервер мог зафиксировать изменения до потери подтверждения.
